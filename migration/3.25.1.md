# Migrate from 3.25.0 to 3.25.1

Provider 3.25.1 is a provider-only release. It continues to target Bytebase
3.25.0 or a compatible development build; no Bytebase 3.25.1 server release is
required. If upgrading from provider 3.24.x or earlier, first follow the
[3.25.0 migration guide](3.25.0.md).

No manual Terraform state migration is required. Existing
`iam_policy { binding {} }` configurations remain supported, with their
existing whole-binding diffs. The new keyed `bindings` form is optional.

## Upgrade Steps

1. Use Terraform 1.1.5 or later. The provider now serves plugin protocol v6
   through the SDK compatibility layer. Features using write-only attributes
   still require Terraform 1.11 or later.
2. Update the provider version constraint, keeping your existing source:

   ```hcl
   terraform {
     required_providers {
       bytebase = {
         source  = "bytebase/bytebase"
         version = "3.25.1"
       }
     }
   }
   ```

3. Run `terraform init -upgrade` and review the updated
   `.terraform.lock.hcl`. For a local build, run `make install` again and keep
   the existing `terraform.local/bytebase/bytebase` source.
4. Run `terraform plan` with its normal refresh enabled before applying.
   Refresh reads policy etags into existing state. Do not use a saved plan
   from the previous provider or `-refresh=false` for the first update.
5. Review the complete IAM policy and effective permission changes before
   applying. Upgrading the provider alone does not migrate legacy HCL to
   keyed bindings or rewrite unchanged policies.

## Optional Keyed Bindings

Keyed bindings give Terraform a stable identity for each binding. Adding a
member or changing a condition then produces a focused diff under that key,
instead of removing and re-adding the whole binding.

Keep the existing `bytebase_iam_policy` resource address and `parent`. Replace
its `iam_policy` block with a `bindings` map, choose stable keys, and preserve
**every** role, member, and condition. Do not configure both forms or add a
second resource for the same parent. No `terraform state rm`, `state mv`, or
re-import is needed.

For example, this is one binding inside an existing legacy policy:

```hcl
iam_policy {
  binding {
    role    = "roles/sqlEditorUser"
    members = ["group:developers@example.com"]

    condition {
      database         = "instances/prod/databases/payments"
      expire_timestamp = "2027-12-31T00:00:00Z"
    }
  }
}
```

The corresponding keyed form is below. Include all other existing bindings
in the same map; this example is not a complete policy to apply unchanged.

```hcl
bindings = {
  developers = {
    role    = "roles/sqlEditorUser"
    members = ["group:developers@example.com"]

    condition = {
      database         = "instances/prod/databases/payments"
      expire_timestamp = "2027-12-31T00:00:00Z"
      environment_ids  = []
    }
  }
}
```

The switch is an in-place resource update, not resource replacement. The plan
will show the legacy block removed and the map added once; later edits use
the stable keys. The provider writes the complete policy in one API call,
not separate revoke/grant calls. Review actual grants, not just the plan size.

### Preserve Environment Restrictions

Inside a legacy condition block, an omitted `environment_ids` is materialized
as an empty set. Its generated `resource.environment_id in []` predicate
denies DDL/DML in every environment. In the keyed form:

- Omitting `environment_ids` means no environment restriction.
- `environment_ids = []` preserves the deny-in-every-environment restriction.
- A nonempty set preserves access to the listed environments only.

The example above therefore includes an explicit empty set. Compare against
the condition returned by the server before migrating. Environment predicates
restrict DDL/DML and are ignored when evaluating other SQL permissions; they
remain stored in the policy. Do not add a condition to an originally
unconditional binding, and do not omit an existing empty-set restriction
unintentionally.

## Whole-Policy Ownership and Drift

The resource still owns the entire policy. Grants added outside Terraform
appear as drift and are removed by the next apply unless added to HCL. Keep
the grants needed by the account running Terraform. Empty policies may be
rejected by the server.

Map entries must have unique role-and-condition identities. If legacy bindings
repeat the same identity, combine their members into one map entry without
dropping any grants. Duplicate remote bindings are read with their members
combined, so an additional grant is not hidden.

Keys are local to Terraform, not stored by Bytebase. Refresh preserves keys
by matching role and condition. Imported policies and unmatched remote
bindings receive generated keys such as `roles/reader#<hash>`. Copy those keys
into configuration or rename them explicitly and review the one-time map
diff. A key rename does not replace the policy resource.

Keyed bindings support the documented structured condition fields. Unsupported
CEL expressions or condition metadata fail clearly rather than being silently
discarded. Inspect and resolve such conditions on the server before adopting
the keyed form; do not reconstruct restricted grants from incomplete legacy
Terraform state.

## Concurrent Policy Changes

When the server supplies an etag, updates of the same parent send the version
retained by refresh. If another writer changes that policy after the plan,
apply fails instead of overwriting it. Refresh, review the latest grants, and
create a new plan; the provider does not automatically retry stale writes.

An update from older state without an etag requires a refresh first. Initial
writes and parent changes read the target policy immediately before writing,
so they do not protect against changes made before that read, including after
planning. If the server returns no etag, including a policy not yet stored,
version-based conflict protection is not available.

See the [IAM resource documentation](../docs/resources/iam_policy.md) and
[setup example](../examples/setup/iam.tf) for the complete schema and usage.
