# Migrate from 3.21.0 to 3.21.1

No state migration is required, and no configuration syntax changes. One behavior change, described below.

## Behavior change: `bytebase_project.issue_labels` is now authoritative

Before 3.21.1, `issue_labels` was declared `Optional + Computed`. Terraform encodes "zero blocks" as an empty collection, the SDK drops empty block collections before computing the diff, and a `Computed` field with nothing in config is treated as "not managed here". Removing *some* of the blocks worked, because a shorter list still reaches the diff - but removing the *last* ones produced `No changes.`, so a project's issue labels could never be emptied through an ordinary apply. Clearing them meant a direct API call, or `terraform state rm` followed by a re-apply.

From 3.21.1 the configuration is authoritative. Removing every `issue_labels` block clears the labels stored in Bytebase:

```hcl
resource "bytebase_project" "sample" {
  resource_id = "sample"
  title       = "Sample"

- issue_labels {
-   value = "retired"
-   group = "type"
-   color {
-     red   = 1
-     green = 0
-     blue  = 0
-   }
- }
}
```

In Terraform JSON, `"issue_labels": []` has the same effect.

### Check your plan before applying

If a project's issue labels were created outside Terraform - in the Bytebase UI, or through the API - and your configuration does not declare them, the next plan shows them being removed:

```
  ~ resource "bytebase_project" "sample" {
      - issue_labels {
          - group = "type" -> null
          - value = "retired" -> null
          ...
        }
    }
```

To keep those labels, declare them in your configuration. This affects only projects that have issue labels the configuration does not list; a project whose labels already match its configuration plans clean.

One case does **not** show up in a plan first. It is not new in 3.21.1 - it already behaved this way in earlier versions - but it is worth knowing while you audit your projects:

- **Terraform adopting a project that already exists in Bytebase.** When a `bytebase_project` is not in state but the project exists on the server, the provider skips the create and issues an update instead. That update has always carried the issue labels from your configuration, so a configuration that omits them wipes the server's labels. The plan for that step shows a resource being created, not labels being removed.

`terraform import` is not in that category. It only writes state, so the labels land in state and the next plan shows them being removed like any other change. That preview is new in 3.21.1 - on earlier versions the deletion was suppressed and the labels simply stayed - so re-plan after importing a project whose labels you mean to keep.

### Keeping labels that are curated in Bytebase

If a project's issue labels are maintained in the Bytebase UI and you would rather not mirror them into your configuration, tell Terraform to ignore the field:

```hcl
resource "bytebase_project" "sample" {
  resource_id = "sample"
  title       = "Sample"

  lifecycle {
    ignore_changes = [issue_labels]
  }
}
```

Terraform then leaves the labels alone on every plan and apply, including applies that change other attributes of the project.

This covers imported projects too, since a `lifecycle` rule shapes the plan for any resource Terraform already tracks. It does not cover adoption: that path builds its request from the configuration before there is a plan at all, so it sends the configuration's issue labels regardless. Keep at least one label in the configuration for a project Terraform might adopt.

### If the project uses `force_issue_labels`

A project with `force_issue_labels = true` rejects the creation of non-draft issues when it has no issue labels (`require issue labels`). Because `force_issue_labels` is `Optional + Computed`, it can be enabled on the server without appearing in your configuration. Check it before clearing a project's labels, and either leave at least one label in place or set `force_issue_labels = false`.

## Not changed: `bytebase_project.labels`

The `labels` map keeps its existing behavior: omitting it leaves the labels stored in Bytebase untouched, and `labels = {}` clears them. Unlike a block collection, a map attribute can express "empty", so it never had the defect above.

## No other changes

Existing state is read as-is; `terraform state rm` / `terraform import` is not required. Resources and data sources not listed above are unaffected.
