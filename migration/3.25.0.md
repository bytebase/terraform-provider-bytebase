# Migrate from 3.24.0 to 3.25.0

Provider 3.25.0 requires Bytebase 3.25.0 or a compatible development build.
Bytebase 3.24.1 does not support the new `disable_download` field.

No manual Terraform state migration is required. Existing resources keep their
IDs and do not need to be removed from state or imported again.

## Upgrade Steps

1. Confirm the server is running Bytebase 3.25.0 or a compatible development
   build before applying the new provider configuration.
2. Update any `disable_export` configuration as described below.
3. Update the provider version constraint, keeping your existing provider source:

   ```hcl
   terraform {
     required_providers {
       bytebase = {
         source  = "bytebase/bytebase"
         version = "3.25.0"
       }
     }
   }
   ```

4. Run `terraform init -upgrade` to select the provider and update
   `.terraform.lock.hcl`.
5. Run `terraform plan` and review the policy and IAM changes before applying.
   The normal refresh reads the new fields into existing state.

Terraform 1.11 or later is required for write-only attributes, including the new
SharePoint application secret. The features below are optional; upgrading the
provider does not enable them or require adding their configuration.

## Query-Data Policy Changes

### Remove `disable_export`

Remove `query_data_policy.disable_export` from every `bytebase_policy` resource.
Provider 3.25.0 rejects `disable_export = true` during validation. Explicit
`false` is still accepted for compatibility, but is deprecated and no longer
sent to Bytebase. Removing it does not recreate the policy.

If the intent is to hide Download in the SQL Editor, replace this block:

```hcl
query_data_policy {
  maximum_result_rows = 100
  disable_export      = true
}
```

with:

```hcl
query_data_policy {
  maximum_result_rows = 100
  disable_download    = true
}
```

This is not an equivalent export-authorization control. `disable_download` is
workspace-level only and hides the SQL Editor's Download destination; it does
not restrict the Export API or configured storage destinations. Manage standing
export permission separately through `bb.sql.export` in roles and IAM bindings.

### Preserve or Change `disable_download`

The resource, policy data source, and policy-list data source now expose
`query_data_policy.disable_download`.

- Set it to `true` to hide Download.
- Set it to `false` to offer Download again.
- Omit it to preserve the current server value, including a restriction already
  migrated on the server. Updating another query-data policy field will not clear
  an omitted download restriction.

Refresh and import read this flag automatically. The deprecated `disable_export`
field is refreshed to `false`; it no longer represents export permission.

## SharePoint Export Configuration

The setting resource and data source now support `name = "settings/EXPORT"`
with an `export.sharepoint` block. This requires a self-hosted server with the
SharePoint export license feature; it is not available in Bytebase Cloud.

```hcl
resource "bytebase_setting" "export" {
  name = "settings/EXPORT"

  export {
    sharepoint {
      tenant_id             = var.sharepoint_tenant_id
      client_id             = var.sharepoint_client_id
      client_secret         = var.sharepoint_client_secret
      client_secret_version = 1
    }
  }
}
```

`client_secret` is sensitive and write-only, so it is not stored in Terraform
state or returned on refresh/import. Use a sensitive, ephemeral input variable
as in the [SharePoint example](../examples/sharepoint/). The data source exposes
only application IDs and `client_secret_set`, not the secret or its local
rotation marker.

`client_secret_version` is a local positive integer, not a server version.
Increment it whenever the secret changes. Changing only the write-only secret
does not schedule an update; unrelated updates do not resend an unchanged
secret. A configured secret requires a version of at least `1`, and a positive
version requires the secret. Imported resources start the marker at `0`.

Failed credential writes retain the previous rotation marker so they can be
retried. Refresh never replays a secret after credentials are cleared outside
Terraform; restore both IDs and increment the marker to supply a new secret.

Omitted IDs preserve their current values. To adopt existing credentials without
replacing the secret, use `export { sharepoint {} }` and omit both secret and
version. To clear the shared application and its secret, apply `export {}`.
Empty ID strings are rejected; removing the required `export` block is not a
clearing operation. Destroying the setting resource preserves credentials and
emits a warning. Clearing them affects every project's SharePoint exports.

The project resource, project data source, and project-list data source now
expose `export_setting.sharepoint.url`:

```hcl
resource "bytebase_project" "reports" {
  resource_id = "reports"
  title       = "Reports"

  export_setting {
    sharepoint {
      url = "https://contoso.sharepoint.com/sites/Finance/Shared%20Documents/Exports"
    }
  }

  depends_on = [bytebase_setting.export]
}
```

Add this block to an existing managed project rather than creating a second
resource for it. The dependency ensures shared credentials exist before the
server resolves the destination. Saving verifies readability, not write access;
the application also needs permission to upload exports. Reads return the
canonical destination URL. Omit the whole `export_setting` block to preserve
the current destination, or apply `export_setting {}` to clear it. These
settings do not grant users the separate `bb.sql.export` permission.

## AI SQL Review Configuration

The setting resource and data source now expose `ai.sql_review_enabled` on
`settings/AI`. Add it to the existing resource managing that setting:

```hcl
ai {
  sql_review_enabled = true
}
```

This is a separate consent switch: review sends change statements to the AI
provider and may send target schemas and table statistics. General AI must also
be enabled and usable. On self-hosted servers, configure the AI provider,
endpoint, model, and credentials separately if they are not already set. In
SaaS, configure only the review toggle; the server manages provider settings.

Enabling review requires the AI SQL review license feature. Setting the switch
to `false` does not require that feature. Omission preserves its current value,
and applying the setting does not start a review. Destroying the setting
resource preserves the server configuration; explicitly set
`sql_review_enabled = false` and apply before removing it to disable review.

### Optional Custom Instructions

`bytebase_policy` and its single/list data sources now support `type = "REVIEW_AI"`
and `review_ai_policy.content`. A custom policy is optional, not a prerequisite
for enabling review. Policy writes require the AI SQL review license feature.

```hcl
resource "bytebase_policy" "ai_review" {
  type = "REVIEW_AI"

  review_ai_policy {
    content = "Require reversible schema changes and flag possible data loss."
  }
}
```

Omit `parent` for the workspace, or set `parent = "projects/{id}"` for a project.
Both levels' instructions apply, with project instructions winning conflicts.
This differs from the replacement behavior of `REVIEW_RULE`. Content must be
nonblank and at most 65,536 bytes. See the [AI review example](../examples/ai_review/)
for a toggle-only configuration with optional custom instructions.

Policies default to `enforce = true`. Creating a policy with `enforce = false`
uses two writes: it is initially created enforced, then disabled. If the second
write fails, the policy may remain enforced. Inspect the actual server policy
and Terraform state before retrying; creation is not an atomic disabled write.

The policy-list data source now includes `REVIEW_AI` policies. Filter consumers
by `type` before accessing a type-specific payload; do not assume a fixed count
or list position.

## IAM Binding Fixes

Database-scoped `bytebase_iam_policy` bindings now accept custom roles whose only
SQL permission is `bb.sql.export`. Previously, the provider rejected these
bindings. Existing custom roles and bindings do not need to be recreated.

The provider now generates valid conditions for database-scoped export and read
grants that also set `condition.expire_timestamp`. No HCL change is required.
Corrected conditions are sent the next time the IAM resource is created or
updated; an unchanged plan does not rewrite existing bindings. Expiration is
preserved, and environment restrictions continue to apply to DDL/DML grants.

## Review Authoritative IAM Plans

`bytebase_iam_policy` still owns the complete policy. If a plan proposes removing
an existing `roles/sqlEditorExporter` binding that should remain, add it to the
corresponding HCL with its members and conditions before applying. Refresh does
not add bindings to configuration.

Compare conditions against the actual server IAM policy, not only refreshed
state. The provider cannot represent every CEL condition, including
`resource.database in [...]` and custom clauses. Do not recreate such bindings
from incomplete state or apply an authoritative policy until all existing
restrictions are represented in configuration.
