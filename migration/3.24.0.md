# Migrate from 3.23.0 to 3.24.0

No manual Terraform state migration is required. Existing resources do not need
to be removed from state or imported again.

The provider now targets the Bytebase 3.24.0 protocol. Some additions below
expose settings that were already available on earlier server versions.

## Upgrade steps

1. Ensure Bytebase server is running 3.24.0 before applying the new provider
   configuration. For self-hosted deployments, follow the
   [server upgrade notes](https://github.com/bytebase/bytebase/releases/tag/3.24.0).
2. Update the provider version constraint:

   ```hcl
   terraform {
     required_providers {
       bytebase = {
         source  = "bytebase/bytebase"
         version = "3.24.0"
       }
     }
   }
   ```

3. Run `terraform init -upgrade` to select the new provider and update
   `.terraform.lock.hcl`. Keep the existing provider source if using a local
   build, and run `make install` again after changing `VERSION`.
4. Run `terraform plan` and review the behavior changes below before applying.
   Refresh may populate newly supported computed fields in state; omitted
   optional/computed fields do not require adding configuration.

Terraform 1.11 or later remains required for write-only attributes.

## Behavior changes

### APP_IM writes and removal now take effect

The provider now sends the per-integration update masks required by Bytebase.
Previously, an APP_IM write could leave the server configuration unchanged.

`bytebase_setting` with `name = "settings/APP_IM"` owns all six supported
integrations: Slack, Feishu, WeCom, Lark, DingTalk, and Teams. Whenever Terraform
writes this setting, omitted integration blocks are removed from Bytebase.
Before the next create or update, include every integration you want to retain
and supply its write-only credentials in configuration or variables. Refresh
and import cannot recover these credentials from Bytebase.

Destroying the APP_IM resource disables all six integrations. Review destroy
plans carefully; removing the resource is not a way to preserve integrations
while stopping Terraform management.

### Policy-list results

`data.bytebase_policy_list` now returns all policy types supported by the
provider: `MASKING_EXEMPTION`, `MASKING_RULE`, `ROLLOUT_POLICY`, `DATA_QUERY`, and
`REVIEW_RULE`. Previously, it returned only the two masking types.

Consumers that assume every result is a masking policy should filter by `type`.
Do not rely on a fixed result count or list position.

## New features

### Project approval by the last plan editor

`bytebase_project.allow_last_plan_editor_approval` controls whether the last plan
editor may approve the issue. The project and project-list data sources expose
the same field. Omit it to leave the server value unchanged; set it explicitly
to `false` to disallow this approval.

### Inactive-session timeout

`bytebase_setting.workspace_profile.inactive_session_timeout_in_seconds` now
configures the workspace inactivity timeout. Add it to the existing resource
managing `settings/WORKSPACE_PROFILE`, rather than creating a second resource
for the same setting.

Omission preserves the current timeout; `0` disables it. Updating this field
requires Bytebase's token-duration-control license feature. The setting data
source also exposes the configured value.

### AI provider settings

`bytebase_setting` and its data source now support `name = "settings/AI"` with
the `ai` block. Self-hosted servers can configure `enabled`, `provider`,
`endpoint`, `api_key`, and `model`. Enabling AI requires an endpoint, model, and
API key in the resulting server setting. For OpenAI, use the full inference
URL; for example, Chat Completions uses
`https://api.openai.com/v1/chat/completions`. `version` is read-only in Bytebase
3.24.0. AI provider settings are server-managed in SaaS mode; use the data source
to read them instead.

Omitted fields remain unchanged. The API key is sensitive but stored in
Terraform state, so protect the state backend. Bytebase redacts the key on
reads; the resource retains the configured value, while the data source returns
an empty key.

Destroying the AI resource preserves the server configuration and emits a
warning. To disable AI on a self-hosted server, set `enabled = false` and apply
before removing the resource.

### MCP capability

`bytebase_setting` and its data source now support `name = "settings/MCP"` with
an `mcp` block. A managed resource must explicitly set `capability` to
`DISABLED`, `READ_ONLY`, or `READ_WRITE`. This is the workspace ceiling; MCP
sessions remain bounded by the connected user's permissions.

Destroying the MCP resource disables MCP for the workspace. See the
[settings example](../examples/settings/) for AI and MCP configuration.

### Standard review-rule policies

`bytebase_policy`, its data source, and its list data source now support
`type = "REVIEW_RULE"` and `review_rule_policy.rules` on workspace and project
parents.

The rule list is the complete enabled set, not additions to inherited rules.
A project policy replaces the workspace selection. An empty list, or a list
without `SYNTAX`, disables all standard review rules. Delete a project policy
to restore the workspace selection, or all rules when there is no workspace
policy. Inheritance applies when rules are evaluated: reading a missing project
policy with `data.bytebase_policy` still returns a not-found error. See the
[policy example](../examples/policies/).
